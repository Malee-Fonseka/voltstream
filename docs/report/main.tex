\section{Use Case and Requirements}
% =====================================================================

\subsection{Scope and Domain Problem}

This report describes \textbf{voltstream}, the data platform we built for Use Case 3 of the
brief, \emph{Smart Grid Energy Monitoring and Billing}. The platform takes in a continuous
stream of smart-meter readings and one tariff file per day, and produces two outputs: a live
dashboard showing the grid by zone, and a daily bill for each household. It uses a
\textbf{Lambda architecture}, for the reasons given in Section~\ref{sec:arch}. All the
figures in the Results section were measured on the running system.

A power grid must balance supply and demand at every moment. Rooftop solar makes this
harder, because the utility cannot control it: when a cloud passes over a zone, solar output
can drop within a minute, and slower power stations have to make up the difference. Knowing
the \emph{renewable contribution of each zone right now} is therefore only useful if the
information arrives quickly. At the same time, the billing department has to bill the same
households from the same readings. A bill combines block tariffs, a fixed charge that
depends on the household's tier, subsidy discounts, and a credit for solar energy exported
to the grid.

\subsection{Interpreted Business Requirements}

The business question in the brief has two parts: \emph{what is the grid load and renewable
contribution in each zone right now}, and \emph{what will each household's bill be once the
daily tariff is applied}. These two parts serve two different users whose needs conflict
(Table~\ref{tab:twoconsumers}), and this conflict drives most of our architecture decision.

The words \emph{once the daily tariff is applied} mean that the final bill depends on data
that does not exist until the day has ended. This is part of the business process, so no
streaming technique can avoid it. The outputs suggested in the brief map onto our system as
follows. Real-time grid load by zone is served by the API endpoint
\texttt{GET /api/v1/zones/load} and shown on the dashboard's Live grid
(Section~\ref{sec:res-live}). The low-renewable alert is the
\texttt{LowRenewableContribution} rule, supported by four further rules that watch the
health of the pipeline (Section~\ref{sec:alerts}). The daily billing and solar report is
available through the API, on the dashboard, and as a Markdown file written for every closed
day (Section~\ref{sec:res-report}).

\subsection{Functional and Non-Functional Requirements}

\begin{enumerate}[label=\textbf{F\arabic*.},leftmargin=2.2em]
  \item Ingest continuous meter readings, and one tariff file (plus a weather file) per
        simulated day.
  \item Keep every raw reading permanently and unchanged, so it can be processed again.
  \item Calculate each zone's load and renewable contribution over short time windows.
  \item Compute per-household daily bills with solar netting, block tariffs, fixed
        charges, subsidy and export credit.
  \item Provide a live dashboard, a daily report, and alerts when values cross a threshold.
\end{enumerate}

\subsection{Simulated Clock}
\label{sec:simclock}

Demonstrating a full real day would take far too long, so the system runs on a faster clock:
\textbf{one simulated day passes in 5 real minutes}, which is 288 times faster than real
time. Simulated time starts at 2026-01-01 00:00 UTC when the system starts, so the first day
is incomplete and 2026-01-02 is the first full day. Each of the 50 meters, spread over 5
zones, sends a reading every 2 real seconds. This gives 150 readings per meter per simulated
day, or about 7{,}500 readings in total. All data is grouped by simulated time, and only
latency is measured with the real clock. A single module converts between the two clocks,
and every duration in the configuration is labelled as either simulated or real, so they
cannot be confused.

\section{Architecture Decision: Lambda versus Kappa}
\label{sec:arch}
% =====================================================================

\textbf{Lambda} \cite{marz} processes the same input data along two paths. A batch layer
periodically recalculates exact results from all the stored data, a speed layer calculates
approximate results from recent data as it arrives, and a serving layer combines the two.
\textbf{Kappa} \cite{kreps} uses a single streaming path and fixes mistakes by re-reading old
data through the same code. \textbf{We chose Lambda.} Table~\ref{tab:archeval} compares the
two against the four criteria named in the marking rubric: latency, replay, cost and
consistency.

\begin{table}[!htbp]
\centering
\caption{Architecture evaluation. Replay and consistency decide it.}
\label{tab:archeval}
\small
\begin{tabularx}{\textwidth}{L{1.9cm} X L{1.9cm}}
\toprule
\textbf{Criterion} & \textbf{Analysis} & \textbf{Verdict} \\
\midrule
Latency &
The two users need answers at very different speeds: seconds for operations, hours for
billing. A single path can only be tuned for one of them. If it waits long for late data,
the operations view is late; if it does not wait, bills are wrong. &
Lambda \\
\addlinespace
Replay &
Billing disputes and tariff corrections can arrive \emph{months} later, but Kafka's
\emph{retention} (how long it keeps messages) is only \emph{days}. Kappa fixes results by
re-reading old messages from Kafka, which is impossible once they have expired. Lambda's
batch layer re-reads from object storage, which keeps data indefinitely. &
Lambda \\
\addlinespace
Cost &
Lambda pays for two sets of code and a burst of computing once a day. Kappa pays for either
very long retention or large amounts of per-household state held for months, a cost that
grows with the number of households. At our scale both are cheap. &
Lambda, narrowly \\
\addlinespace
Consistency &
Billing needs a permanent, auditable record that does not depend on the message system, so
that every bill can be traced to its readings. Lambda's \emph{master dataset}, a permanent
copy of every raw reading, provides this. In Kappa the only record is Kafka's log, which is
deleted according to a retention policy. &
Lambda, decisively \\
\bottomrule
\end{tabularx}
\end{table}

\paragraph{The rejected alternative.} Kappa would also have worked here. Tariffs would be
stored in a Kafka topic that keeps only the latest tariff for each household, a single Spark
streaming job would join them to the readings, and corrections would be made by re-reading
old messages into a new table. Its main advantages are a single codebase, so the two paths
can never disagree, one job to run, and one design to understand. We rejected it for three
reasons. First, bills may need to be recalculated months later, but Kafka keeps messages for
only days, so Kappa's way of correcting results would not be available when billing needs
it. Second, a financial audit trail should not depend on how long a message system is
configured to keep data. Third, holding billing state for every household for months is more
expensive and more fragile than running one bounded job each night.

\paragraph{Lambda's cost and how we contain it.} With Lambda, the same billing logic exists
in two places, and the two copies can drift apart without anyone noticing. For example, if
the speed layer ended the first tariff block at 60\,kWh and the batch layer ended it at
61\,kWh, households near that boundary would see two different bills. To prevent this, all
the netting, tariff, rounding, key and validation logic lives in one shared module, which
only performs calculations, is fully tested, and is used by both layers. The logic still has
to exist in two forms, because the API calculates estimates without Spark while the Spark
jobs need Spark's own expressions. To prove that the two forms agree, a consistency test runs
both on 5{,}000 random inputs, and on values either side of every tariff block boundary, and
checks that they produce the same bill to the cent. A difference in the logic would
therefore fail a test. Differences in the inputs, such as a stale tariff or dropped late
readings, are expected, and we measure them while the system runs
(Section~\ref{sec:res-recon}).

\paragraph{What would reverse the decision.} Lambda is only justified while the stored raw
data has to outlive Kafka's retention. If Kafka's tiered storage, or a table format such as
Apache Iceberg or Delta Lake, gave the log unlimited and queryable history, Kappa's single
codebase would become the better choice.

\paragraph{The three views.} The \emph{master dataset} contains every raw reading,
unchanged, stored as Parquet files (a compressed, column-oriented format) on object storage
and organised by simulated date and hour. It is never modified, and the archiver does not
filter anything out, so any bug can be fixed later by recalculating from it. The \emph{speed
view} holds 15-minute (simulated) windows for each zone, with consumption, solar generation,
renewable ratio and active meters, together with a running provisional bill for each
household. That bill uses \emph{yesterday's} tariff, because today's tariff does not exist
yet. The \emph{batch view} is built when a day's tariff file arrives: the whole day is read,
validated, cleaned of duplicates, joined with that day's tariff and billed, and the result
is then compared with the speed view.

\paragraph{The merge function.} When a household's bill is requested for a day, the API
checks the \emph{run ledger}, a table recording every billing run. If the batch layer has
already billed that day, the API returns the final bill; otherwise it returns the speed
layer's provisional estimate (Figure~\ref{fig:merge}). The batch bill always takes priority,
because it includes the late readings that the speed layer missed and uses the correct
tariff. Every response states which layer produced it and which day's tariff was used.

\paragraph{Key transformations.} Readings are grouped into time windows by \textbf{event
time}, which is when the meter took the reading, rather than when the reading arrived,
because readings can arrive out of order. A \emph{watermark} sets how long the speed layer
waits for late readings before it closes a window. \textbf{Solar netting} is applied before
the tariff:
\begin{equation*}
  \mathit{self} = \min(\mathit{solar}, \mathit{consumption}),\quad
  \mathit{import} = \mathit{consumption} - \mathit{self},\quad
  \mathit{export} = \mathit{solar} - \mathit{self},
\end{equation*}
The bill is then $\mathit{total} = \mathit{energy\_charge} + \mathit{fixed\_charge} -
\mathit{subsidy} - \mathit{export\_credit}$, where the energy charge prices the imported
energy block by block, and money is rounded half-up to two decimal places in exactly the
same way in both layers. Because Kafka may deliver the same reading twice, both layers
\textbf{remove duplicates} using the meter ID and reading time, a rule defined once in the
shared module. Kafka messages are keyed by household, so each household's readings stay in
order.

\section{Technology Stack and Justification}
\label{sec:stack}
% =====================================================================

\paragraph{Kafka.} Kafka \cite{kafka} is a log rather than a queue: reading a message does
not delete it. This means a bug in the speed layer can be fixed by re-reading old messages,
the producer keeps working when a reader is down, and the speed layer and the archiver can
read the same topic independently. We confirmed that stopping one reader did not affect the
other. The topic has three partitions, which limits how many readers can work in parallel,
and Kafka's default seven-day retention is the limitation discussed in
Section~\ref{sec:arch}. RabbitMQ was rejected because it deletes a message once it has been
read, so it supports neither re-reading nor independent readers.

\paragraph{Spark.} Spark \cite{spark} uses the same programming interface for batch and
streaming jobs, so a single billing module can serve both layers. This directly addresses
Lambda's biggest risk. Spark also supports event-time windows and watermarks natively. Storm
offers lower latency, but it has no event-time windows and no batch interface, and since we
only need answers within seconds, its extra speed would not help us. Flink is a stronger pure
streaming engine, but it does not offer an equally simple way to share batch code in Python,
and Spark already meets our latency target (6.3\,s against a 60\,s limit).

\paragraph{Parquet on object storage.} Lambda needs every raw reading to be kept. If a bill
is wrong because of a logic error, such as using \texttt{>} instead of \texttt{>=} at a
block boundary, the fix is to correct the code and recalculate from the raw readings.
Parquet stores data by column, compresses it well, keeps proper data types and lets queries
skip data they do not need, and organising the files by date and hour means the daily job
reads only its own day. We use a local S3-compatible object store so that markers do not
need a cloud account; because the code uses only the standard S3 interface, moving to AWS S3
would only require a configuration change. Since MinIO stopped publishing its images, the
system runs \texttt{pgsty/silo}, a MinIO-compatible replacement. HDFS was rejected as too
heavy for a system of this size.

\paragraph{PostgreSQL.} Our queries look up a household's bill for a date, total the recent
readings for each zone, and join bills with the run ledger and household details, all of
which return small, relational results. PostgreSQL supports joins, transactions (so a billing
run is saved completely or not at all), JSON columns for the block breakdown, and writes that
can safely be repeated. Cassandra is designed for much higher write volumes than ours, and it
does not support joins.

\paragraph{Airflow.} Airflow \cite{airflow} schedules work by real time, so ``once per
simulated day'' cannot be written as a normal schedule. Instead, a small workflow (a
\emph{DAG}) called \texttt{tariff\_watcher} checks the landing zone every real minute and
starts the \texttt{daily\_billing} workflow once for each new tariff file. Each run is named
after the file's date (\texttt{billing\_\_2026-01-02}), so the same day is never billed twice
by accident, and re-billing a day simply starts another run for that date
(\texttt{billing\_\_2026-01-02\_\_r1}). The workflows only start Spark jobs and check their
results; they contain no billing logic. Cron was rejected because it has no task
dependencies, retries, run history or re-runs.

\paragraph{Prometheus, Alertmanager and Grafana.} Each service publishes its metrics, and
Prometheus \cite{prometheus} collects (\emph{scrapes}) them every 15 seconds. Batch jobs
finish too quickly to be collected this way, so they push their metrics to a Pushgateway
instead. The alert rules are stored in the repository and tested with \texttt{promtool}, and
the Grafana dashboards are created automatically from files.

\subsection{Data Sources and Ingestion}

Two Python programs simulate the data sources. The \textbf{meter producer} calculates each
household's consumption and solar generation for the current simulated time (solar is zero
between 18:00 and 06:00), adds random variation, and publishes a reading to the Kafka topic
\texttt{meter.readings} every 2 seconds:

\begin{lstlisting}[caption={A meter reading event, keyed by \texttt{household\_id}.},label={lst:event}]
{"schema_version": "1.0", "event_id": "uuid4", "trace_id": "uuid4",
 "meter_id": "MTR-0042", "household_id": "HH-0042", "grid_zone": "ZONE-C",
 "event_ts": "2026-01-02T14:15:00Z",          // simulated time; drives all windowing
 "consumption_kwh": 0.412, "solar_generation_kwh": 0.180, "voltage": 232.4, "producer_id": "sim-01"}
\end{lstlisting}

The \textbf{reference dropper} writes two files to the landing zone for each simulated day: a
tariff file (for each household: tier, subsidy flag, three block rates, fixed charge, export
rate and effective date) and a weather file. Tariff rates change by $\pm$0.50 each day, so
using yesterday's tariff makes a visible difference. The formats of the readings, tariffs
and weather records are fixed as schemas, and every tariff row is checked before it is used.

To test how robust the pipeline is, the producer deliberately introduces faults at
configurable rates (Appendix A): duplicate readings, readings with missing fields or negative
values, readings from unknown households, and \emph{meter dropouts}, where a meter loses its
connection, stores its readings and sends them late once it reconnects. \emph{Reordering},
where readings arrive slightly out of order, is introduced separately. Invalid readings are
sent to a dead-letter topic (\texttt{meter.readings.dlq}) and recorded, with the reason, in
the \texttt{rejected\_records} table. A test checks that when every fault rate is set to
zero, the output is identical to the input.

\subsection{Processing}

\paragraph{Raw archiver.} This Spark streaming job writes every Kafka message to Parquet
without changing it, organised by simulated date and hour, and after a restart it continues
from where it stopped. It guarantees that \emph{no data is lost}, but not that each reading
is written exactly once: Spark saves the files and its reading position in two separate
steps, so a crash between them causes a small range to be read again. After deliberately
killing the archiver, we found 334 duplicate rows out of 14{,}012 and no missing readings;
the batch layer removes such duplicates.

\paragraph{Speed layer.} A second, independent Spark streaming job checks each reading with
the shared validation rules, removes duplicates, and groups the readings into 15-minute
(simulated) windows for each zone, using a 30-minute (simulated) watermark. It also keeps a
running total for each household, and writes its results to PostgreSQL every 10 real
seconds; this interval is called the \emph{trigger}. The provisional bill is calculated with
the shared billing logic and yesterday's tariff.

Running the clock 288 times faster has two side effects here. First, 10 real seconds equals
48 simulated minutes, which is longer than the 30-minute watermark, so in practice it is the
trigger interval, not the watermark, that decides which late readings are dropped (see
Section~\ref{sec:res-recon}). Second, results are published after every trigger, so the
watermark does not delay them; it only decides when old windows are closed.

\paragraph{Batch layer.} The \texttt{daily\_billing} workflow has eight tasks, which run in
this order: wait for the day's tariff file; wait a further 90 real seconds for late
readings; run the Spark billing job, which reads the day's Parquet files, validates them,
removes duplicates, joins the tariff, applies the shared netting and tariff logic, writes the
bills and records the run in the run ledger; check that the number of bills is correct; check
that every bill adds up; calculate exact daily totals for each zone and check that they match
the household totals; reconcile the two layers; and write the daily report.

\paragraph{Reconciliation.} For each household, the difference between the speed estimate and
the final bill is split into two parts. The \emph{tariff effect} is the part caused by using
yesterday's prices: the speed layer's energy priced at today's tariff, minus its estimate.
The \emph{data effect} is the rest: the final bill minus that re-priced figure, which reflects
readings the speed layer missed. The two parts always add up to the total difference.

\subsection{Code Quality and Testing}

The \texttt{service} and \texttt{stage} fields show which part of the pipeline wrote each

stream as everything else.

\subsection{Resilience and Re-billing}
\label{sec:res-resilience}
\label{sec:res-restate}

\paragraph{Crashing each path.} We stopped the raw archiver abruptly (\texttt{SIGKILL}) for
20\,s. No readings were lost and there were no gaps in Kafka; the 334 duplicates this caused
were removed by the batch layer. We then stopped the speed layer for 60\,s. During that time
the live view was 56\,s out of date, while the archiver continued to store readings (1{,}526
of them). After restarting, the speed layer caught up within 22\,s, the previous day's final
bill stayed at 237.38, and the day of the crash was still billed in full. In other words,
when the speed layer fails, the live view is briefly out of date, but no bill is affected.

\paragraph{Re-billing a day.} The \texttt{voltstream.ps1 backfill} script deliberately
corrupted the tariff for 2026-01-02 (adding 45.00 to the block 1 rate), re-billed the day,
restored the correct file and re-billed it again. The day's total went from 18{,}737.41 to
44{,}876.57 and then back to exactly 18{,}737.41. The run ledger shows the three runs as
\texttt{superseded}, \texttt{superseded} and \texttt{success}, each linked to its own Airflow
run, and \texttt{household\_bill\_history} keeps all three versions of every bill. Bills are
always recalculated from the stored raw data, never edited directly.

\section{Discussion, Limitations and Production Scale}
\label{sec:limitations}
\label{sec:discussion}
% =====================================================================

\paragraph{Was Lambda the right choice?} We think so. The provisional bill was always going
to differ from the final one, because it uses yesterday's tariff, and the batch layer
replaced it with the correct bill about 2.5 minutes after each day closed. Re-billing a past
day tested the main reason we rejected Kappa: we recomputed the day from the stored Parquet
files, without relying on Kafka still holding the data. Lambda did cost more, as
expected (two jobs, an orchestrator and a reconciliation step), but because both layers
share one billing module, every difference between them came from their inputs, never
from the billing logic.

\paragraph{Limitations.}
\begin{itemize}
  \item \textbf{Time compression} speeds up simulated time but not the computer's processing
        time, so the watermark settings are not realistic. This is why the trigger interval
        ended up longer than the watermark, and why the live view misses about 1\% of the
        energy. Setting the watermark longer than one trigger interval would fix this.
  \item \textbf{Simulation:} meters send the energy used in each interval rather than a
        running total; consumption, solar and tariffs are synthetic; and 50 households is far
        fewer than a real utility serves. The weather file is produced but is not used for
        billing or solar generation.
  \item \textbf{Small files:} one simulated day produced 245 Parquet files averaging only
        10.2\,kB, far smaller than Parquet works best with. A production system would need to
        merge them regularly, or use a table format that does so.
  \item \textbf{Single points of failure:} there is one Kafka broker, one Spark node and one
        PostgreSQL server, no schema registry, and passwords are stored as local defaults in
        \texttt{.env}.
  \item \textbf{Resources:} the system needs about 9\,GB of memory. On the demonstration
        laptop the divergence test ran out of memory, so that alert was demonstrated with a
        lower threshold.
  \item \textbf{Monitoring gaps:} if \texttt{sql-exporter} stops, two alerts stay silent
        instead of firing, and the Pushgateway keeps showing the last divergence value
        indefinitely. Tracing uses correlation IDs rather than full distributed tracing.
\end{itemize}

\paragraph{Production scale.} In production we would use Iceberg or Delta Lake on top of the
raw Parquet files (for transactions, automatic merging of small files and access to past
versions), a schema registry with Avro or Protobuf, change data capture instead of daily
tariff files, replicated Kafka, Spark on Kubernetes, watermarks based on measured delays, and
alerts for when the exporters themselves stop. PostgreSQL would be enough for up to a few
million summary rows per day; beyond that, a column-oriented database such as ClickHouse
would fit better. Iceberg or Kafka tiered storage would also remove the retention limit that
decided Section~\ref{sec:arch}, at which point Kappa would become the better choice.

% =====================================================================
\section{Conclusion}
\label{sec:conclusion}
% =====================================================================

Voltstream uses one stream of meter readings to serve two very different needs. Grid
operators need the load and renewable share of each zone within seconds, while billing needs
an exact, auditable bill that cannot be produced until the daily tariff arrives. We chose
Lambda because bills must be recalculable long after Kafka has deleted the original
messages, and we limited Lambda's main risk by sharing all billing logic through one tested
module. The system is built with Kafka, Spark, Parquet on object storage, PostgreSQL, Airflow
and FastAPI, and starts with a single command. On the running system, the speed path
delivered zone metrics in about 6 seconds; the batch layer finalised all 50 bills about 2.5
minutes after each day closed; each bill switched from provisional to final as designed; a
corrupted day was re-billed with its history kept; neither crash lost any data; and all five
alerts fired when their faults were introduced. The main limitation is the compressed clock,
which distorts the timing of the streaming path. The architecture decision itself would only
change if Kafka's data could be kept and queried indefinitely.
