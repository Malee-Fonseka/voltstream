Lambda architecture

One stream, two layers, one answer

Fifty simulated smart meters stream readings into Kafka. A speed layer turns them into live, approximate figures within seconds. A batch layer recomputes each closed day from the immutable master dataset and produces the authoritative bill. The API merges the two: final if the batch layer has closed the day, otherwise the speed layer's estimate, labelled as such.

The merge function

The whole of Lambda's promise reduces to a choice between two rows. The API makes it on every request:

if the day has a 'success' row in pipeline_runs:
    serve household_bill_daily   # source: batch, provisional: false
else:
    serve household_running_rt   # source: speed, provisional: true

The batch row wins whenever it exists: it saw the late data the speed layer dropped and applied the day's own tariff. Once the day is reconciled the difference is explained exactly: estimate − final = tariff effect + data effect.

Observability

Every service exposes Prometheus metrics, and every log line is structured JSON carrying the reading's trace_id. Five alert rules live in the repository as code:

  • MeterDataStale a zone stopped reporting
  • LowRenewableContribution solar share below threshold
  • HighRejectRate too many readings rejected
  • BatchSLAMiss a closed day was not billed in time
  • LambdaDivergenceHigh speed and batch disagree too much

Reading this dashboard

Provisional
A speed-layer estimate. Changes as readings arrive and uses yesterday's tariff.
Final
The batch layer's bill for a closed day. Does not change unless the day is restated.
Window
A 15-simulated-minute bucket of readings. The newest is still filling.
Renewable share
Solar generation as a share of consumption, capped at 100%.
Speed-layer lag
How far the newest window trails simulated now: roughly one trigger interval.
Tariff effect / data effect
The two causes of the gap between estimate and final: the stale tariff and the readings the speed layer never counted.
